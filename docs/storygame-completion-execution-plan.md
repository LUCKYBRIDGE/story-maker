## 0. 실행 결론

현재는 기능형 MVP와 G0~G6·A1-01 완료 기록을 바탕으로, 사용자가 고른
목업 방향에 맞춰 네 화면을 정합화하는 **U1 프로그램**을 준비한다.

메인 A → 독립 이야기 구성 → 대본·컷 두 보기 → 원작을 참고한 플레이를 연결한다.
기존 작품·Excel·다중 단계·화자와 이미지의 독립성을 보존하며 전면 재작성하지 않는다.
현재 차이, 순서, 검증과 새 세션 지시는 **§11**이 현재 실행 계획이다.
구체적 카드 범위는 원자 작업 카드, 지금 시작할 한 작업은 상태표만 결정한다.

이전 G1 작품 안전성 → G2 글쓰기 흐름 → G3 구조 → G4 교실 안정성 프로그램과
완료 증거는 아래에 보존한다. 이미 완료된 데이터 계층을 다시 만들라는 지시가 아니다.
내부 QA 기록과 실제 학생 파일럿은 구분하며 계정·클라우드·분기는 별도 결정이다.

## 1. 완성 목표

### 1.1 학생 사용자 이야기

> 처음 온 학생으로서, 설명을 길게 읽지 않고 이야기의 첫 장면을 써서 5분 안에
> 플레이하고 싶다. 그래야 도구를 배우는 대신 내 이야기를 만들 수 있다.

> 다시 온 학생으로서, 이 기기의 마지막 작업과 이전 버전을 분명하게 찾고 싶다.
> 그래야 실수하거나 화면이 닫혀도 작품을 잃지 않는다.

> 글을 고치는 학생으로서, 대본과 장면 꾸미기와 플레이를 오간 뒤에도 같은
> 챕터와 장면으로 돌아오고 싶다. 그래야 이야기의 흐름을 놓치지 않는다.

### 1.2 교사 사용자 이야기

> 수업을 운영하는 교사로서, 로그인과 네트워크 문제 없이 학생들이 시작하고,
> 작품을 Excel로 보관하고, 문제가 생겼을 때 스스로 복구하게 하고 싶다.

> 국어 교사로서, 도구가 학생의 문장을 대신 쓰지 않으면서 인물의 바람, 갈등,
> 사건의 인과와 결말의 변화를 생각하게 하고 싶다.

### 1.3 개발·운영 사용자 이야기

> 유지보수 개발자로서, 저장·도메인·화면·파일 변환을 독립적으로 변경하고
> 실제 학생 흐름으로 회귀 여부를 확인하고 싶다.

### 1.4 완성의 핵심 지표

| 지표 | 목표 |
|---|---|
| 첫 플레이 시간 | 처음 사용자 중앙값 5분 이내 |
| 작품 복구 | 새로고침·중단·불러오기 실패 뒤 직전 안전본 복구 가능 |
| 위치 유지 | 대본↔장면↔메모 왕복 뒤 같은 장면과 입력 위치 유지 |
| 오류 해결 | 학생이 오류 안내에서 한 번의 선택으로 문제 입력에 도달 |
| 핵심 접근성 | 키보드만으로 새 작품→첫 플레이 완료 |
| 파일 호환 | 최신·이전 Excel, 긴 글·줄바꿈·빈 메모 왕복 보존 |
| 회귀 보호 | 핵심 9개 사용자 흐름을 배포 전 자동 검사와 수동 절차로 확인 |

## 2. 2026-09-03 개발 현황

### 2.1 검증된 기반

- 로그인 없는 시작과 빈 작품 만들기
- 기기 저장본 이어하기, 예시 플레이와 세 이어쓰기 템플릿
- 3·4·5단계 이야기 구성과 한 장의 여러 단계 연결
- 자유·인물·관계·장소·사건 창작 메모
- 대본 전체와 컷 꾸미기
- 화자 이름과 이미지의 독립 편집
- 추천/전체·검색·태그·즐겨찾기·최근 사용 이미지 선택
- 편집본과 플레이 버전 분리
- 최신/이전 Excel과 공개 Google 시트의 공통 변환 경로
- 공식 Excel 8개 탭과 현재 자산 카탈로그 리소스

### 2.2 당시 실행 기준선과 최신 기록

아래 83개 기록은 이전 정리 시점의 역사다. 이후 A1-01 완료 기록에는 check와
전체 90/90이 있다. 이번 2026-09-04 계획 세션에서는 위치·상태·단계·핵심 흐름
좁은 검사 20/20만 새로 실행했다. 전체 검사·새 UI 실화면을 재검증한 것은 아니다.

| 검사 | 결과 | 해석 |
|---|---|---|
| lint + TypeScript | 통과 | 현재 소스의 정적 오류 없음 |
| 프로덕션 빌드 | 통과 | 배포 산출물 생성 가능 |
| 현재 Node 회귀 검사 | 83/83 통과(2026-09-03 재검증 전 기준) | 템플릿·Excel·저장·편집·다중 단계 흐름 유지 |
| 번들 | 경고 있음 | 최소화 후 500KB를 넘는 청크 존재 |

검사 통과는 실제 모바일 키보드, 모달 초점, 저장 할당량과 긴 작품 편집까지
검증했다는 뜻은 아니다.

### 2.3 완성도 지도

| 영역 | 현재 수준 | 가장 큰 남은 문제 | 다음 문턱 |
|---|---|---|---|
| 제품 방향 | 강함 | 완성 범위와 확장 범위가 섞일 위험 | 경계 유지 |
| 교육 구조 | 강함 | 플레이 후 고쳐쓰기 안내가 약함 | 자기 점검 순환 |
| 핵심 편집 | 중상 | 커서·스크롤·undo·모바일 키보드 | 흐름 신뢰성 |
| 저장·복구 | 구현 기반 있음 | localStorage 할당량·손상·실기기 검증 | 기존 봉투·체크포인트 보호 및 재검증 |
| Excel·시트 | 중상 | 공백 보존, 상세 오류와 미리보기 | 호환성 신뢰 |
| 접근성 | 중 | 모달 초점과 작은 글자 | 키보드·저시력 완성 |
| 성능 | 중 | 큰 청크와 원본 이미지 목록 | 측정 기반 최적화 |
| 코드 구조 | 중 | 2,968줄 상위 화면과 약 8,300줄 CSS | 저장·Dialog·스타일 책임 추가 분리 |
| 자동 검증 | 중상 | 83개 데이터·상태·정적 UI 검사, 실제 브라우저 검증 부족 | 브라우저·기기 테스트 |
| 교실 운영 | 미검증 | 실제 수업 관찰 자료 부족 | 파일럿과 개선 반복 |

### 2.4 현재 문서 위험

- 기존 소스의 종이·민트와 새 목업의 네이비·흰색·청록은 서로 다른 시점이다.
  토큰 문서에 현재값과 목표값을 분리했고 U1-03에서 범위를 제한해 적용한다.
  문서 갱신을 실제 CSS 변경으로 간주하지 않는다.
- 기존 아키텍처 문서는 실제 디렉터리·저장·데이터 흐름을 설명하지 못해 이번에
  현재 구조와 목표 이동 순서를 기록했다.
- 현재 대규모 기능 변경이 아직 커밋되지 않았으므로 다음 코드 작업 전에는 변경
  범위와 기준선을 다시 확인해야 한다.

## 3. 페르소나 운영 모델

### 3.1 페르소나 정의

#### A. 학생 창작 제품 책임자

- 책임: 첫 성공, 핵심 흐름, 범위와 우선순위
- 성공 질문: 이 변경이 학생이 더 빨리 쓰고 더 안전하게 고치게 하는가?
- 거부 조건: 기능 수는 늘지만 첫 화면과 핵심 흐름이 복잡해짐

#### B. 학생 대변인

- 책임: 처음 보는 용어, 읽기 부담, 선택 피로, 실수 복구
- 성공 질문: 설명 없이도 다음 행동을 예상할 수 있는가?
- 거부 조건: 아이콘 추측, 12px 미만 필수 문구, 실수 후 되돌릴 길 없음

#### C. 초등 국어 교사

- 책임: 목표–갈등–사건–변화, 대사·해설 구분, 고쳐쓰기
- 성공 질문: 학생의 사고를 돕되 답을 대신 만들지 않는가?
- 거부 조건: 모든 칸을 정답처럼 강제하거나 자동 완성으로 학생 문장을 대체함

#### D. 아동문학 작가·편집자

- 책임: 예시, 템플릿, 도움말, 오류 문장의 정확성과 여백
- 성공 질문: 짧고 자연스러우며 다양한 이야기를 허용하는가?
- 거부 조건: 추상적인 칭찬, 장황한 안내, 하나의 모범답안으로 수렴

#### E. 교육 UX 디자이너

- 책임: 정보 위계, 글쓰기 우선, 반응형, 터치와 상태 피드백
- 성공 질문: 가장 중요한 입력과 현재 위치가 첫눈에 보이는가?
- 거부 조건: 같은 기능 반복, hover 의존, 설정이 글보다 앞섬

#### F. 접근성 검토자

- 책임: 키보드, 화면 읽기, 확대, 색 대비, 움직임 감소
- 성공 질문: 마우스와 시각 정보 없이도 핵심 흐름이 가능한가?
- 거부 조건: 초점 유실, 모달 밖 이탈, 색만으로 상태 표현

#### G. 프런트엔드 아키텍트

- 책임: 모듈 경계, 상태 전이, 성능과 유지보수성
- 성공 질문: 기존 동작을 보존하면서 독립적으로 테스트 가능한가?
- 거부 조건: 전면 재작성, UI와 데이터 마이그레이션을 한 변경에 혼합

#### H. 데이터 신뢰성 엔지니어

- 책임: 저장, 복구, 스키마 버전, ID와 이전 데이터 호환
- 성공 질문: 중간 실패와 이전 형식에서도 작품이 보존되는가?
- 거부 조건: 마이그레이션 없는 저장 구조 변경, 손상본으로 정상본 덮어쓰기

#### I. 호환성 엔지니어

- 책임: Excel·Google 시트·CSV, 공식 양식과 이전 양식
- 성공 질문: 무엇이 틀렸는지 탭·행·열과 해결 방법까지 알 수 있는가?
- 거부 조건: 조용한 데이터 손실, 본문 공백·줄바꿈의 무조건 정리

#### J. 개인정보 보호자

- 책임: 미성년자 정보, 파일·본문·외부 URL의 최소 수집
- 성공 질문: 이 데이터를 정말 저장하거나 전송해야 하는가?
- 거부 조건: 작품 본문 기본 수집, 정책 없는 업로드·계정·공개 공유

#### K. QA·릴리스 책임자

- 책임: 인수 조건, 회귀 검사, 실제 사용자 흐름과 릴리스 증거
- 성공 질문: 통과를 재현할 수 있는 증거가 있는가?
- 거부 조건: 빌드 성공만으로 UI 완료 선언, 테스트 비활성화

#### L. 교실 운영 교사

- 책임: 수업 시간, 기기·네트워크 차이, 파일 배포와 회수, 교사 개입 비용
- 성공 질문: 한 차시 안에 여러 학생이 막힘 없이 시작·보관·발표하는가?
- 거부 조건: 교사가 학생마다 로그인·파일·복구 문제를 대신 해결해야 함

#### M. 미디어 자산 편집자

- 책임: 이미지 분류, 표시 품질, 저작권, 썸네일, 파일 크기와 캐릭터 기준본
- 성공 질문: 학생이 안전한 자료를 빠르게 찾고, 같은 캐릭터의 감정이 바뀌어도
  머리·몸·발 위치가 튀지 않는가?
- 거부 조건: 출처 불명, 과도한 용량, 캐릭터·배경 분류 혼합, 기준본 없는 포즈
  양산, 비균일 확대나 머리만 따로 바꾸는 보정

## 4. 의사결정 원칙

### 4.1 우선순위 점수

후보 작업은 아래 항목을 0~3점으로 평가한다.

- 작품 손실 방지
- 첫 플레이 시간 단축
- 글쓰기·고쳐쓰기 품질
- 교실 운영 안정성
- 접근성
- 이후 개발 위험 감소
- 구현·마이그레이션 위험(감점)

작품 손실 가능성이 있는 문제는 점수와 관계없이 P0이다. P2 확장 기능은 G1~G4
문턱을 통과하기 전에는 시작하지 않는다.

### 4.2 기능을 추가할 조건

새 기능은 다음 질문에 모두 `예`일 때만 핵심 범위에 넣는다.

1. 명확한 학생 또는 교사 과업이 있는가?
2. 기존 기능을 발견하기 어려운 문제로 오인한 것은 아닌가?
3. 로그인·네트워크 없이도 핵심 흐름을 유지하는가?
4. 저장·Excel·플레이 데이터에 미치는 영향이 정의되었는가?
5. 모바일·키보드·오류·복구 상태가 설계되었는가?
6. 자동 또는 반복 가능한 검증 방법이 있는가?

### 4.3 필수값을 추가할 조건

플레이에 필요한 제목, 챕터, 장면 본문과 대사 화자 이외의 구상 입력은 원칙적으로
선택이다. 교육적으로 유용하다는 이유만으로 플레이를 막지 않는다.

### 4.4 클라우드·업로드 경계

- 여러 기기 작품 저장이 확정되기 전에는 D1을 반쯤 도입하지 않는다.
- 학생 이미지 업로드가 확정되기 전에는 R2와 파일 소유권 구조를 추가하지 않는다.
- 계정이 필요해져도 로그인 실패가 로컬 제작을 막지 않게 별도 경로를 유지한다.
- 공개 공유 전에는 미성년자 개인정보, 저작권, 신고·삭제 운영을 먼저 결정한다.

## 5. 완성 프로그램과 문턱

### G0. 현재 기준선 고정

목표: 이미 구현한 기능을 잃지 않고 다음 작업을 시작한다.

주 책임: QA·릴리스 책임자
검토: 프런트엔드 아키텍트, 학생 창작 제품 책임자

작업:

1. 현재 대규모 변경을 기능별 검토 단위로 구분한다.
2. 최신 로컬 저장본, 이전 저장본, 최신·이전 Excel과 손상 파일 fixture를 만든다.
3. 핵심 사용자 흐름 9개를 반복 가능한 절차로 고정한다.
4. 실제 디자인 토큰과 문서 우선순위를 일치시킨다.
5. 번들·이미지·긴 작품 성능 기준선을 기록한다.

통과 조건:

- 정적 검사, 빌드와 현재 회귀 검사가 통과한다.
- 기준 fixture의 출처와 기대 결과가 문서화된다.
- 변경 전후를 비교할 핵심 흐름이 정의된다.

### G1. 작품을 믿고 맡길 수 있음

목표: 새로고침, 실수, 손상과 가져오기 실패 뒤에도 작품을 되찾는다.

주 책임: 데이터 신뢰성 엔지니어
검토: 호환성 엔지니어, 개인정보 보호자, QA·릴리스 책임자

#### Slice 1 — 작품 문서 버전

- `schemaVersion`, ISO `savedAt`, 앱 버전 메타데이터
- `crypto.randomUUID()` 기반 새 ID
- 전체 프로젝트 normalize와 validate
- v1 로컬 저장본을 현재 형식으로 바꾸는 마이그레이션
- 손상본을 정상본과 분리하여 보존

인수 조건:

- 현재 v1 저장본이 내용 손실 없이 열린다.
- 빠진 선택 필드는 기본값으로 복원된다.
- 중복 ID와 끊어진 챕터–장면 연결을 탐지한다.
- 마이그레이션 실패가 현재 정상본을 덮어쓰지 않는다.

#### Slice 2 — 저장소와 저장 상태

- 작품 저장소 인터페이스
- 300~800ms 지연 자동 저장
- `저장 중 / 이 기기에 저장됨 / 저장 실패` 상태
- 탭 숨김·종료 전 남은 저장 처리
- 환경설정과 작품 데이터 저장 분리

인수 조건:

- 빠른 연속 입력에서도 마지막 내용이 저장된다.
- 저장 실패 이유와 Excel 보관 경로가 안내된다.
- 저장 상태가 플레이 적용 상태와 혼동되지 않는다.

#### Slice 3 — 체크포인트와 복구

- 가져오기·플레이 반영·삭제 전 자동 체크포인트
- 최근 10~20개 또는 용량 기준 복구 이력
- 같은 내용 중복 체크포인트 방지
- 삭제 직후 되돌리기
- Excel 파일명 `작품제목_YYYYMMDD_HHmm.xlsx`

인수 조건:

- 학생이 복구본의 시각과 발생 이유를 이해한다.
- 복구를 취소해도 현재 작품이 보존된다.
- 브라우저 데이터 삭제·기기 교체는 복구할 수 없음을 정확히 안내한다.

G1 통과 증거:

- 새로고침, 중간 종료, 저장 실패, 손상 v1, 가져오기 실패, 삭제 복구 시나리오 통과
- 최신·이전 Excel 왕복 통과

### G2. 학생이 흐름을 잃지 않고 씀

목표: 화면 조작보다 이야기 읽기와 고쳐쓰기에 집중한다.

주 책임: 교육 UX 디자이너
검토: 학생 대변인, 초등 국어 교사, 접근성 검토자

#### Slice 4 — 장면 명령과 위치 유지

- 장면 추가·삽입·이동·복제·삭제를 순수 명령으로 추출
- 새 장면 본문으로 초점 이동
- 대본↔장면 꾸미기 왕복 시 장면과 스크롤 복원
- 텍스트 기본 undo와 충돌하지 않는 구조 변경 undo
- 긴 챕터의 장면 찾기

인수 조건:

- 20개 장면에서 작업해도 현재 위치를 잃지 않는다.
- 장면 순서 변경 뒤 번호와 플레이 순서가 일치한다.
- 삭제 후 즉시 되돌릴 수 있다.

#### Slice 5 — 오류에서 수정으로 바로 이동

- 플레이 적용 문제를 위치별 목록으로 제공
- 오류 항목 선택 시 챕터·장면·입력으로 이동
- 오류 입력의 초점과 잠시 지속되는 강조
- 오류와 선택적 고쳐쓰기 제안을 분리

인수 조건:

- 학생이 오류 문구만 보고 고칠 장소와 행동을 안다.
- 오류가 없는 구상 빈칸은 플레이를 막지 않는다.

#### Slice 6 — 창작 메모 왕복 완성

- 챕터·장면 연결을 메모 UI에서 선택
- 검색 결과→메모→원래 대본 초점 복귀
- 모바일 전체 화면의 명확한 돌아가기
- 메모 삭제 되돌리기

인수 조건:

- 메모는 플레이에 나타나지 않는다.
- 검색·수정·닫기 뒤 학생이 쓰던 장면으로 돌아온다.

#### Slice 7 — 고쳐쓰기 순환

- 플레이 끝의 `편집으로 돌아가 고치기`
- 대본 하단의 비채점형 자기 점검
- 인물 목표, 장면 인과, 대사·해설 반복, 결말 변화 질문
- `확인함 / 나중에`만 저장하고 점수화하지 않음

인수 조건:

- 도움말이 작품 문장에 자동 삽입되지 않는다.
- 학생이 선택한 구조에 맞는 질문만 보인다.
- 고쳐쓰기 없이도 플레이는 가능하다.

G2 통과 증거:

- 390×844, 768×1024, 1024×768, 1440×900에서 핵심 흐름 확인
- 키보드만으로 빈 작품→첫 플레이 완료
- 학생 5명 이상 관찰에서 첫 플레이 중앙값 5분 이내

### G3. 개발자가 안전하게 변경함

목표: 기능 변경을 독립적으로 검증하고 회귀를 빠르게 발견한다.

주 책임: 프런트엔드 아키텍트
검토: QA·릴리스 책임자, 교육 UX 디자이너

#### Slice 8 — 도메인·상태 분리

- project command, validation, migration, selector 분리
- reducer로 작품 변경 명령 통합
- 임시 UI 상태와 작품 데이터 분리
- 테스트에서 React 없이 핵심 명령 실행

#### Slice 9 — 저장·외부 변환 분리

- local repository와 환경설정 저장소 분리
- Excel·Google 시트 어댑터와 공통 오류 모델
- 본문 원문과 구조 판정용 정규화 값 분리
- 앞뒤 공백·쉼표·따옴표·줄바꿈 fixture

#### Slice 10 — 화면과 CSS 분리

- 공통 Dialog와 Asset Picker부터 분리
- 시작→구상→대본→장면→플레이 순서로 컴포넌트 분리
- 실제 토큰 사용, 12px 미만 필수 문구 제거
- 화면별 CSS 이동과 중복 미디어 쿼리 정리

전면 재작성과 시각 재설계를 동시에 하지 않는다. 각 이동 단계는 기존 화면과
동작을 유지해야 한다.

#### Slice 11 — 테스트 피라미드

- 순수 도메인 단위 테스트
- 마이그레이션·import/export fixture 테스트
- 모달·초점·저장 상태 컴포넌트 테스트
- 핵심 사용자 흐름 9개
- 대표 화면 크기와 키보드 수동 검사 체크리스트

G3 통과 증거:

- 주요 작품 변경 명령이 React 없이 테스트된다.
- StoryStudio는 조립과 상위 흐름 중심으로 축소된다.
- 문자열 존재가 아니라 실제 상태 전이를 검증하는 테스트가 핵심 기능을 보호한다.
- 한 화면 변경이 관련 컴포넌트와 스타일 안에서 리뷰 가능하다.

### G4. 실제 교실에서 반복 사용 가능

목표: 네트워크·기기·읽기 수준 차이가 있는 수업에서 안정적으로 사용한다.

주 책임: 교실 운영 교사
검토: 학생 창작 제품 책임자, 접근성 검토자, QA·릴리스 책임자

#### Slice 12 — 가져오기 경험

- 탭·행·열·현재 값·해결 방법이 있는 오류 목록
- 치명적 오류와 경고 분리
- 챕터·장면·메모 수와 바뀌는 내용을 보여 주는 미리보기
- 공개 시트가 아닐 때 공개 설정과 Excel 대체 경로
- Google 요청 시간 제한과 취소

#### Slice 13 — 성능과 오프라인

- 이미지 160~320px 썸네일
- 현재 챕터 자료 우선 로딩과 화면 밖 지연 로딩
- Excel 변환 시간 측정 후 필요할 때만 Worker 검토
- 앱 셸과 핵심 자료 캐시
- 새 앱 버전과 사용자 작품 저장의 캐시 분리

#### Slice 14 — 접근성 마감

- 공통 Dialog focus trap과 복귀
- 12px 미만 필수 문구, 44px 미만 조작 목록 제거
- 색 대비, 200% 확대, 움직임 감소
- 플레이 키보드 이동과 현재 장면 읽기
- 모바일 키보드가 열린 상태 확인

#### Slice 15 — 교실 파일럿 준비와 내부 QA

- 처음 사용자, 이어쓰기, Excel 복구를 포함한 수업 시나리오
- 학생의 막힘을 설명 부족, 용어, 위치 유실, 데이터 문제로 분류
- 교사 개입 횟수와 첫 플레이 시간 기록
- 작품 본문은 기본 분석 자료로 수집하지 않음
- 한 번에 상위 3개 문제만 다음 반복에 반영

G4 통과 증거:

- 첫 로드 뒤 통신이 끊겨도 로컬 편집·플레이·Excel 저장 가능
- 저사양 대표 태블릿에서 긴 작품 입력이 수업을 방해하지 않음
- 학생·교사 파일럿의 P0 문제가 해결되고 반복 수업에서 재현되지 않음

### A1. 캐릭터 포즈 세트가 같은 배우로 보임

목표: 캐릭터의 감정·동작 이미지가 바뀌어도 몸 크기, 머리/몸 비율, 눈높이와
발 위치가 안정적으로 유지된다.

주 책임: 미디어 자산 편집자
검토: 프런트엔드 아키텍트, QA·릴리스 책임자

#### Slice A1-01 — 기준본과 자동 Audit

- `작품 + 인물 + 디자인 + 변형 + 구도`별 승인 기준본
- `800×1200`, 투명 알파, `groundY=1149`, 가장자리 잘림 검사
- 몸통 시각 중심, 눈높이, 중심 신체 높이와 머리/몸 비율 보고
- 귀·더듬이·뿔·손·소품을 전체 크기 기준에서 제외
- 캐릭터별 기준본+전체 Pose 비교표 생성

#### Slice A1-02 — 후보 세트 승인과 1:1 등록

- `KEEP / NORMALIZE-TRANSLATE / NORMALIZE-UNIFORM-SCALE /
  REFERENCE-REMAKE / REJECT` 판정
- 보정 전 원본 보존과 원본 기반 1회 인코딩
- 균일 변환으로 해결할 수 없는 파일만 기준본을 넣어 재생성
- 승인 뒤 기존 asset ID·파일명·StoryProject 참조를 유지하여 1:1 교체
- 실제 무대의 좌·우 배치와 대표 화면 크기에서 위치 튐 확인

A1 통과 증거:

- 등록 대상 전신 자산이 캔버스·알파·바닥선 자동 검사를 모두 통과
- 캐릭터별 비교표에서 기준본 대비 비율 차이가 허용 범위 안이거나 수동 판정 기록
- 감정 전환 무대에서 캐릭터가 공중에 뜨거나 갑자기 대두·소두로 보이지 않음
- 재생성 대상은 평행이동·균일 확대/축소로 해결할 수 없는 파일로 제한

## 6. 기존 핵심 사용자 흐름 9개와 U1 추가 인수

1. **빈 작품**: 시작 → 제목 → 첫 챕터 → 첫 대사 → 적용 → 플레이
2. **이어쓰기**: 템플릿 선택 → 빈 장면 작성 → 앞뒤 장면 플레이
3. **창작 메모**: 틀 선택 → 추천 항목 → 검색 → 수정 → 원래 장면 복귀
4. **Excel 왕복**: 저장 → 다시 불러오기 → 구상·메모·챕터·장면 동일
5. **오류 복구**: 잘못된 파일 → 오류 위치 → 현재 작품 유지 → 복구
6. **기기 복구**: 편집 → 새로고침 → 최근 작업 이어하기 → 같은 위치
7. **모바일 글쓰기**: 키보드 열기 → 장면 추가 → 메모 → 적용 → 플레이
8. **다중 단계 연결**: 한 장에 위기·절정 연결 → 구조 전환 → 연결 복원
9. **단계 Excel 왕복**: 여러 단계 저장 → 다시 불러오기 → 적용·플레이

각 흐름은 결과뿐 아니라 초점, 현재 위치, 저장 상태와 플레이 버전 분리를
확인한다. U1은 CF-10~13(진입 보호, 구성 왕복, 플레이 컷 수정, 반응형 입력)을
추가 계획한다. 이 4개는 아직 자동화·실행 완료가 아니며 QA 문서에 분리한다.

## 11. U1 화면 정합화 실행 계획

### 11.1 목표·판단·비목표

- 주 책임: 교육 UX 디자이너. 필수 검토 관점: 초등 국어 교사, 프런트엔드 아키텍트.

의존 순서를 잡은 이유:

1. 먼저 실제 화면·필드·사용자 확인을 고정한다. 이미지 파일의 비율을 CSS로 옮기지 않는다.
2. 위치/진입 상태를 안정시킨 뒤 셸과 메인을 바꿔 작품 교체·복귀 회귀를 줄인다.
3. 구성을 간단히 만든 뒤 장 순서/기본 무대 조작을 붙인다. 변경 범위를 분리한다.
4. 공통 무대 계약을 먼저 만든 뒤 편집·플레이가 같은 연출을 사용하게 한다.
5. 플레이 동작(인덱스/수정/예시 격리)과 표현을 다른 카드에서 검증한다.
6. 마지막에 저장·Excel·반응형을 통합 검증한다. UI 완료를 캐릭터 세트 승인이나
   실수업 파일럿 완료로 확대 해석하지 않는다.

| 첫 진입·기기 읽는 중·실패 | 두 진입, 안내·복구 선택 | 예시를 저장본으로 오인, 읽기 실패 뒤 덮어쓰기 |

실제 iOS/Android 키보드·수업 관찰은 내부 뷰포트 모의와 분리해 기록한다.
할 수 없는 검수는 미실행으로 남기고 해당 릴리스 문턱을 통과 처리하지 않는다.

### 11.5 변경·중단·되돌리기

- 이 계획 정비는 문서/지침만 바꾼다. package.json, 잠금 파일, tsconfig,
  빌드·호스팅·배포 설정은 바꿀 근거가 없어 유지한다.
- UI 개선 중 실제 작품 손실 위험을 발견하면 외형보다 먼저 막고 최소 회귀를
  추가한다. 카드 범위를 넘으면 위험·재현·별도 수정 카드를 기록한다.
- 사용자 미커밋 변경을 기준으로 이번 카드 diff를 분리한다. 파일 전체 되돌리기,
  초기화, 생성 자산 정리로 과거 작업을 지우지 않는다.
- 새 의존성·스키마·라우팅·클라우드가 필요하다는 결론이 나오면 자동 확대하지
  말고 별도 결정으로 중단한다.
- 카드마다 좁은 검사→check→test→실제 흐름을 확인한다. 신규 픽셀 레이아웃을
  정적 문자열 검사 통과만으로 완료하지 않는다.
- U1-11 뒤 미해결 P1을 먼저 별도 카드로 처리하고, 없으면 A1-02 재개 조건을
  점검한다. 유예가 자산 승인을 생략해도 된다는 의미는 아니다.
