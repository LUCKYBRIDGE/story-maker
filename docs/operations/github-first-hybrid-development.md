# GitHub-first 하이브리드 개발 운영 계약

- 기준일: 2026-09-13
- 대상 저장소: `LUCKYBRIDGE/story-maker`
- 목적: GitHub를 단일 공유 기준선으로 유지하면서 Chat과 Codex Work가 **중복 분석·중복 검증 없이 같은 milestone을 연속 진행**하도록 한다.
- 상위 규칙: `AGENTS.md`, `docs/storygame-ai-implementation-runbook.md`

## 1. 핵심 원칙

1. `main`은 승인·통합된 기준선, 작업 branch/PR은 진행 중 기준선이다.
2. Chat/Work 중 더 짧은 피드백 루프를 가진 쪽이 주도한다.
3. 한 번에 하나만 `IN_PROGRESS`로 둔다.
4. 현재 작업이 `DONE`이고 다음 의존 작업이 명확하면 같은 milestone 안에서 **사용자 응답을 기다리지 않고 계속한다.**
5. 같은 정보·문서·검증을 여러 환경에서 반복하지 않는다.
6. 장시간 로컬 전용 상태를 만들지 않고 의미 있는 체크포인트마다 같은 branch/PR에 동기화한다.

## 2. 주도권

### Chat Lead
GitHub 안의 정보만으로 충분한 로직·데이터·문서·테스트·PR/CI 작업.

### Work Lead
브라우저·로컬 파일·자산·runtime·IME·scroll·성능·OS/장치 피드백이 핵심인 작업.

### Joint
계약/테스트는 Chat, 실제 화면·runtime 반복 수정은 Work처럼 역할을 나누되 같은 branch/PR을 사용한다.

주도권은 도구 사용률이 아니라 **정보 접근성 + 피드백 속도 + 필요한 증거**로 결정한다.

## 3. 세션 시작 — 최소 문맥

Work/로컬은 우선 `npm run status:check`를 사용한다.

그 뒤 다음만 읽는다.

1. 현재 `READY`/`IN_PROGRESS`
2. 해당 작업 카드의 관련 절
3. 영향받는 소스와 가장 가까운 테스트
4. 실제 충돌이나 결정이 있을 때만 상세 설계·ADR·목업 추가 조회

장기 로드맵, 완료 이력 전체, 모든 카드, 모든 ADR을 세션마다 다시 읽지 않는다.

## 4. 증거는 필요한 것만

- **G** GitHub: 실제 파일, branch/commit/PR diff
- **A** 자동: 관련 test/check/CI
- **B** 브라우저/로컬: 실제 UI·IME·scroll·파일 흐름
- **D** 장치/OS: 실기기에서만 확인 가능한 동작

작업에 필요한 종류만 수집한다. Work라고 해서 모든 B/D를 요구하지 않고 Chat이라고 해서 B/D가 필요한 작업을 A만으로 끝내지 않는다.

## 5. 최소 검증 원칙

검증은 가장 가까운 범위에서 시작한다.

- 문서/지침: 링크·경로·충돌만 확인, build/test 생략
- 국소 로직/데이터: 가장 가까운 단위/회귀 테스트
- UI: 관련 자동 검사 + 대표 흐름 1~2개
- 저장/스키마/Excel/호환성: 관련 fixture와 회귀 범위 확대
- 전체 `npm test`/smoke: 릴리스 후보, 공용 핵심 코드, 빌드/의존성, 넓은 blast radius에서만

같은 commit에서 CI가 이미 통과한 명령은 Work에서 반복하지 않는다. CI/로컬 차이 자체가 문제일 때만 반복한다.

## 6. 연속 실행

```text
READY → IN_PROGRESS → DONE
                     ↓
        다음 의존 작업이 명확하고 안전함
                     ↓
           바로 다음 작업 계속
```

다음 경우에만 기본적으로 멈춘다.

- milestone 완료
- 다음 단계가 불명확하거나 실제 요구 충돌
- 데이터 손실/호환성 파괴 위험
- canonical 자산·제품 계약 변경 필요
- main merge, 공개 배포, force push, 비용, 권한/비밀정보 변경
- 동일 원인 재시도 3회 실패

작업이 정상 진행 중이라는 이유로 멈추지 않는다.

## 7. 동기화와 handoff

- 같은 파일을 Chat과 Work가 동시에 수정하지 않는다.
- 로컬 dirty change는 먼저 보존한다.
- 의미 있는 체크포인트에서 commit/push한다.
- handoff는 저장소 전체 재설명이 아니라 다음만 넘긴다.

```text
작업/milestone:
branch/PR:
현재 HEAD:
완료한 것:
실제 검증:
다음 작업:
남은 위험/미검증:
```

## 8. 보고

작은 원자 작업마다 장문 보고하지 않는다. milestone 체크포인트에서만 짧게 보고한다.

```text
[완료] 핵심 결과
[검증] 실제 실행한 최소 검증
[다음] 바로 이어갈 작업
```

## 9. 권한 경계

되돌릴 수 있는 작업 branch/commit/push/draft PR과 CI 조회는 구현 흐름 안에서 수행할 수 있다.

다음은 명시적 승인 없이는 하지 않는다.

- main merge
- 공개 배포
- force push
- 사용자 데이터 삭제
- 외부 비용 발생
- 비밀정보·권한 변경

## 10. 운영 목표

- 저장소 전체 재분석 최소화
- 동일 문서 재독 최소화
- 중복 검증 최소화
- 상태 문서 중복 작성 최소화
- 정상 진행 중인 Work의 불필요한 중단 최소화
- 필요한 안전성은 유지하면서 실제 제품 완성 속도 최대화
