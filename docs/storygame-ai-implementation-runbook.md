## 1. 이 문서가 해결하는 문제

장기 계획만 읽은 AI는 여러 단계를 한꺼번에 구현하거나, 완료 증거 없이 다음
기능으로 이동하거나, 이미 수정 중인 파일을 덮어쓸 수 있다. 따라서 이 프로젝트는
다음 네 가지를 분리한다.

| 문서 | 한 가지 책임 |
|---|---|
| 상세 설계 | 무엇을 만들 것인가 |
| 완성 실행 계획 | 왜 이 순서로 완성하는가 |
| 개발 상태표 | 지금 실행할 수 있는 작업은 무엇인가 |
| 원자 작업 카드 | 그 작업의 허용 범위와 완료 증거는 무엇인가 |

## 2. 절대 규칙

1. 한 세션은 `READY` 상태의 작업 **하나만** 수행하고 멈춘다.
2. `READY`가 둘 이상이면 구현하지 말고 상태표 오류를 고친다.
3. 명시된 선행 작업이 모두 `DONE`이 아니면 시작하지 않는다.
4. 작업 카드의 허용 파일 밖은 수정하지 않는다.
5. 기존 미커밋 변경은 사용자 작업이다. 삭제·되돌리기·대체하지 않는다.
6. 인수 조건과 검증 명령이 모두 통과하기 전에는 `DONE`으로 바꾸지 않는다.
7. 실패한 검사를 지우거나 약화해서 통과시키지 않는다.
8. 사용자가 실제 구현을 요청한 세션에서는 작업 브랜치 생성, 커밋, push, draft PR까지는
   되돌릴 수 있는 기본 GitHub 작업으로 수행할 수 있다. main merge, 공개 배포, 강제 push,
   데이터 파괴, 외부 비용 발생은 사용자가 그 세션에서 명시할 때만 한다.
9. 계정·클라우드는 이어만들기의 미래 수단으로 고려하되 현재 구현 범위가 아니다.
   공동 편집, 공개 공유, 학생용 생성 AI도 별도 결정 전에는 추가하지 않는다.
10. 한 작업을 끝내면 다음 작업이 `READY`가 되었더라도 같은 세션에서 시작하지 않는다.

## 3. 세션 시작 순서

공통 순서는 유지하되 실행 환경에 맞는 증거만 요구한다.

1. 실행 환경을 판별한다.
   - **GitHub 연결 Chat**: GitHub에서 default branch, 현재 main HEAD, 작업 브랜치,
     열린 PR과 상태표를 확인한다. 로컬 경로나 `git status` 부재를 중단 사유로 삼지 않는다.
   - **Work/로컬**: `/Volumes/WAN2/apps/story-maker`와 실제 `git status`를 확인한다.
     원격 작업 브랜치를 checkout하고 로컬 미커밋 변경을 먼저 보존한다.
2. `AGENTS.md`를 처음부터 끝까지 읽는다.
3. `docs/storygame-development-status.md`를 읽고 유일한 `READY` 작업을 찾는다.
4. 이 런북, `docs/operations/chat-first-development.md`, 해당 원자 작업 카드를 읽는다.
5. 카드가 지정한 제품 문서, 소스, 테스트를 읽는다. U1 화면 작업은
   `docs/design/mockups/README.md`와 화면 흐름 ADR도 읽는다. 이미지의 예문·숫자·
   잘린 인물·모순된 버튼을 사양으로 복제하지 않는다.
6. 아래 작업 계약을 짧게 작성한 뒤 구현한다.

```text
작업 ID:
실행 등급: C1 / C2 / W1 / W2
한 문장 목표:
주 책임 / 필수 검토 페르소나:
허용 파일:
비목표:
인수 조건:
자동 검증:
Work/실기기 검증:
중단 조건:
```

## 4. 상태 전이

```text
BLOCKED --(모든 의존성 DONE + 카드 완성)--> READY
READY   --(사전 점검 통과)---------------> IN_PROGRESS
IN_PROGRESS --(모든 인수 조건·검증 통과)--> DONE
IN_PROGRESS --(중단 조건 발생)------------> BLOCKED
READY/BLOCKED --(명시적 우선순위 유예)----> DEFERRED
DEFERRED --(재개 결정 + 선행 조건 충족)--> READY
```

- READY는 실행 대기 작업 하나다. 그 작업을 IN_PROGRESS로 바꾼 동안에는
  READY가 0개인 것이 정상이며 다음 작업을 동시에 열지 않는다.
- 승인 대기 등으로 모두 BLOCKED이면 이유·재개 조건을 기록하고 멈춘다.
- 세션 시작 직후 사전 점검이 끝나기 전에는 상태를 바꾸지 않는다.
- 실제 파일 편집을 시작할 때 `READY → IN_PROGRESS`로 바꾼다.
- `DONE` 행에는 날짜, 검증 명령, 핵심 결과를 짧게 기록한다.
- 중단 시 원인을 재현할 증거와 재개 조건을 기록하고 `BLOCKED`로 바꾼다.
- 다음 작업은 의존성이 모두 `DONE`이고 카드 내용이 현재 코드와 일치할 때만
  `READY`로 바꾼다.

## 5. 구현 절차

### 5.1 사전 점검

- 카드의 허용 파일이 작업 브랜치/PR에서 이미 수정되어 있으면 기존 diff를 먼저 읽는다.
- Work/로컬에서 미커밋 변경이 있으면 사용자 작업으로 보존하고 원격 diff와 분리한다.
- 기존 변경과 분리할 수 없거나 의도가 충돌하면 구현하지 않고 중단한다.
- 카드에 필요한 타입, 호출 경로, 저장 키, 오류 경로를 실제 코드로 확인한다.
- GitHub 연결 Chat은 실행할 수 없는 로컬 검사를 실행했다고 쓰지 않는다. 가능한 정적 확인과
  테스트 추가를 먼저 수행하고, push 후 CI 결과를 자동 검증 증거로 사용한다.
- Work/로컬은 카드가 요구한 로컬/실기기 검증만 수행하며 CI에서 이미 통과한 동일 명령을
  이유 없이 반복하지 않는다.

### 5.2 최소 구현

- 테스트 또는 관찰 가능한 인수 조건 하나를 먼저 고정한다.
- 프로덕션 변경은 그 조건을 만족하는 최소 범위로 제한한다.
- UI, 데이터 구조, 파일 형식 변경을 한 작업에 섞지 않는다.
- 새 의존성, 새 서비스, 전면 재작성은 카드에 명시되지 않으면 금지한다.
- 생성 파일은 생성기나 원본을 수정한 뒤 공식 명령으로 다시 만든다.

### 5.3 검증

아래 순서에서 불필요한 넓은 검사를 먼저 실행하지 않는다.

1. 변경 파일에 가장 가까운 단위 검사 또는 해당 회귀 검사를 코드로 고정
2. GitHub PR CI: `npm run check`, `npm test`, 커밋 diff whitespace 검사
3. 작업 카드가 요구하는 추가 호환 검사
4. W1/W2인 경우에만 Work/로컬에서 실제 브라우저·IME·파일·실기기 흐름
5. GitHub 최종 PR diff와, Work를 사용했다면 로컬 `git status`

CI에서 성공한 동일 `npm run check`/`npm test`를 Work가 다시 실행하는 것은 기본
절차가 아니다. CI와 로컬 결과가 달라질 가능성이 있는 환경 문제를 조사할 때만 반복한다.

캐릭터 이미지 생성·보정 작업은 코드 빌드만으로 완료하지 않는다. 기준본과 전체
Pose 비교표를 만들고, `800×1200`, 알파, `groundY=1149`, 가장자리 잘림을 자동
검사한 뒤 실제 무대의 좌·우 배치에서 확인한다. 발선·위치 문제는 먼저 평행이동,
전신 크기 문제는 머리/몸 비율이 같을 때만 균일 확대·축소한다. 부분 변형이
필요하면 기준본을 넣어 재생성한다.

문서만 바꾸는 작업은 링크, 경로, 상태 수, 중복·충돌을 검사한다. 다만 현재
기준선 통과를 새로 기록할 때는 실제 명령을 실행해야 한다.

## 6. 실패와 재시도 규칙

- 같은 원인에 대한 수정 시도는 최대 3회다.
- 매 시도마다 증상, 원인 가설, 바꾼 점, 결과를 구분한다.
- 세 번째에도 실패하면 검사를 우회하지 말고 `BLOCKED`로 전환한다.
- 요구사항이 모호해도 기존 문서와 코드로 낮은 위험 결정을 할 수 있으면 보수적으로
  진행한다. 데이터 손실, 공개 범위, 비용, 인증처럼 결과가 크게 달라질 때만 묻는다.
- 관련 없는 기존 검사 실패는 숨기지 않는다. 작업 전에도 실패했는지 비교하고
  현재 작업과의 인과를 보고한다.

## 8. 작업 카드 완전성 검사

작업 카드는 아래 항목이 하나라도 없으면 실행할 수 없다.

- 작업 ID와 선행 작업
- 학생·교사 가치
- 주 책임과 필수 검토 페르소나

- 사전 점검

- 정확한 검증 명령
- 중단·되돌리기 조건
- 상태표 갱신 방법

## 10. 계획 변경 규칙

- 제품 범위나 교육 목표가 바뀌면 상세 설계와 완성 실행 계획을 먼저 갱신한다.
- 순서·의존성만 바뀌면 상태표와 해당 작업 카드를 갱신한다.
- 구현 중 새 위험을 발견하면 현재 카드의 인수 조건을 몰래 넓히지 않는다.
  현재 작업을 안전하게 끝낼 수 없으면 막힘으로 기록하고 별도 작업을 만든다.
- 완료된 카드의 기록은 지우지 않는다. 후속 수정은 새 작업 ID를 만든다.

- 사용자가 직접 계획·지침 재정비만 요청한 세션은 구현 READY를 실행하지 않는다.
  문서 작업 ID를 기록하고 기존 작업을 보존한 채 우선순위를 갱신할 수 있다.
- 미승인 시안을 임의로 확정하지 않는다. 구성 01은 2026-09-04 사용자 위임으로
  채택했으므로 재승인을 묻지 않는다. U1-01의 실제 검증이 끝나기 전에는 레이아웃
  구현(U1-03 이후)을 READY로 열지 않는다. 예외적으로 U1-02의 위치·진입 상태 계약은
  U1-00과 확인된 소스/DOM 기준선을 선행으로 수행한다. 자체 검사·실제 왕복 인수는
  그대로 필요하다. U1-03은 U1-01과 U1-02 모두 DONE이어야 한다.
  목업 복사본은 문서 자산이며 public/에 넣지 않는다.
- 이미 DONE인 카드의 당시 '다음 작업' 문구는 현재 상태표보다 우선하지 않는다.


## 11. Chat ↔ Work handoff

GitHub PR을 handoff의 단위로 사용한다.

### Chat에서 Work로 넘길 때

다음만 전달한다.

```text
작업 ID / 실행 등급:
PR / branch:
CI 결과:
Work에서만 확인할 항목:
정확한 viewport·기기·입력:
재현 절차:
수정 권한: 보고만 / 같은 branch에서 최소 수정 허용
```

Work에 저장소 전체 재감사나 이미 끝난 설계 논의를 반복시키지 않는다.

### Work에서 Chat으로 돌려줄 때

```text
환경:
실행한 검증:
PASS:
FAIL:
재현 절차:
스크린샷·로그 위치:
코드 수정 여부:
수정했다면 commit SHA:
```

Work가 코드를 수정했다면 장시간 로컬 전용 상태로 남기지 않고 같은 작업 브랜치에
커밋·push한다. 이후 원격 PR이 다시 공유 기준선이다.

### 완료 판정

- C1: GitHub diff와 문서 정합성 증거로 완료할 수 있다.
- C2: 필수 CI가 통과하면 Work 없이 완료할 수 있다.
- W1: CI + 카드가 요구한 Work/실브라우저 증거가 모두 있어야 한다.
- W2: CI가 필요한 경우 통과하고, 실제 장치/OS 증거까지 있어야 한다.
- 실행하지 않은 증거는 PASS로 간주하지 않는다.
