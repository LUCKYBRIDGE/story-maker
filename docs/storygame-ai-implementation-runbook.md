# storygame AI 구현 런북

- 기준일: 2026-08-24
- 대상: 성능 차이가 있는 AI 개발 세션과 사람 검토자
- 목적: 한 세션이 한 개의 작은 작업만 안전하게 완료하게 하는 공통 절차
- 현재 작업 상태: `docs/storygame-development-status.md`
- 작업별 계약: `docs/tasks/storygame-atomic-task-cards.md`
- 제품·단계 기준: `docs/storygame-completion-execution-plan.md`

## 1. 이 문서가 해결하는 문제

장기 계획만 읽은 AI는 여러 단계를 한꺼번에 구현하거나, 완료 증거 없이 다음
기능으로 이동하거나, 이미 수정 중인 파일을 덮어쓸 수 있다. 따라서 이 프로젝트는
다음 네 가지를 분리한다.

| 문서 | 한 가지 책임 |
|---|---|
| 상세 설계 | 무엇을 만들 것인가 |
| 완성 실행 계획 | 왜 이 순서로 완성하는가 |
| 개발 상태표 | 지금 실행할 수 있는 작업은 무엇인가 |
| 원자 작업 카드 | 그 작업의 허용 범위와 완료 증거는 무엇인가 |

## 2. 절대 규칙

1. 한 세션은 `READY` 상태의 작업 **하나만** 수행하고 멈춘다.
2. `READY`가 둘 이상이면 구현하지 말고 상태표 오류를 고친다.
3. 명시된 선행 작업이 모두 `DONE`이 아니면 시작하지 않는다.
4. 작업 카드의 허용 파일 밖은 수정하지 않는다.
5. 기존 미커밋 변경은 사용자 작업이다. 삭제·되돌리기·대체하지 않는다.
6. 인수 조건과 검증 명령이 모두 통과하기 전에는 `DONE`으로 바꾸지 않는다.
7. 실패한 검사를 지우거나 약화해서 통과시키지 않는다.
8. 커밋·푸시·배포·외부 서비스 변경은 사용자가 그 세션에서 명시할 때만 한다.
9. 계정, 클라우드 저장, 공동 편집, 공개 공유, 학생용 생성 AI는 현재 범위가 아니다.
10. 한 작업을 끝내면 다음 작업이 `READY`가 되었더라도 같은 세션에서 시작하지 않는다.

## 3. 세션 시작 순서

순서를 바꾸지 않는다.

1. `/Volumes/WAN2/apps/story-maker`가 존재하는지 확인한다. 없으면 즉시 중단한다.
2. 저장소 루트, 브랜치, 원격 저장소, `git status`를 확인한다.
3. `AGENTS.md`를 처음부터 끝까지 읽는다.
4. `docs/storygame-development-status.md`를 읽고 유일한 `READY` 작업을 찾는다.
5. 이 런북과 해당 원자 작업 카드만 먼저 읽는다.
6. 카드가 지정한 제품 문서, 소스, 테스트를 읽는다.
7. 아래 작업 계약을 짧게 작성한 뒤 구현한다.

```text
작업 ID:
한 문장 목표:
주 책임 / 필수 검토 페르소나:
허용 파일:
비목표:
인수 조건:
검증 명령:
중단 조건:
```

## 4. 상태 전이

```text
BLOCKED --(모든 의존성 DONE + 카드 완성)--> READY
READY   --(사전 점검 통과)---------------> IN_PROGRESS
IN_PROGRESS --(모든 인수 조건·검증 통과)--> DONE
IN_PROGRESS --(중단 조건 발생)------------> BLOCKED
```

- 세션 시작 직후 사전 점검이 끝나기 전에는 상태를 바꾸지 않는다.
- 실제 파일 편집을 시작할 때 `READY → IN_PROGRESS`로 바꾼다.
- `DONE` 행에는 날짜, 검증 명령, 핵심 결과를 짧게 기록한다.
- 중단 시 원인을 재현할 증거와 재개 조건을 기록하고 `BLOCKED`로 바꾼다.
- 다음 작업은 의존성이 모두 `DONE`이고 카드 내용이 현재 코드와 일치할 때만
  `READY`로 바꾼다.

## 5. 구현 절차

### 5.1 사전 점검

- 카드의 허용 파일이 이미 수정되어 있으면 기존 diff를 먼저 읽는다.
- 기존 변경과 분리할 수 없거나 의도가 충돌하면 구현하지 않고 중단한다.
- 카드에 필요한 타입, 호출 경로, 저장 키, 오류 경로를 실제 코드로 확인한다.
- 가장 좁은 사전 검사를 한 번 실행해 시작 기준을 기록한다.

### 5.2 최소 구현

- 테스트 또는 관찰 가능한 인수 조건 하나를 먼저 고정한다.
- 프로덕션 변경은 그 조건을 만족하는 최소 범위로 제한한다.
- UI, 데이터 구조, 파일 형식 변경을 한 작업에 섞지 않는다.
- 새 의존성, 새 서비스, 전면 재작성은 카드에 명시되지 않으면 금지한다.
- 생성 파일은 생성기나 원본을 수정한 뒤 공식 명령으로 다시 만든다.

### 5.3 검증

아래 순서에서 불필요한 넓은 검사를 먼저 실행하지 않는다.

1. 변경 파일에 가장 가까운 단위 검사
2. 타입·정적 검사: `npm run check`
3. 작업 카드가 지정한 호환·빌드 검사
4. 릴리스 경로를 바꾼 경우: `npm test`
5. 보이는 UI 변경인 경우: 카드가 지정한 실제 흐름과 화면 크기
6. 최종 diff와 `git status`

문서만 바꾸는 작업은 링크, 경로, 상태 수, 중복·충돌을 검사한다. 다만 현재
기준선 통과를 새로 기록할 때는 실제 명령을 실행해야 한다.

## 6. 실패와 재시도 규칙

- 같은 원인에 대한 수정 시도는 최대 3회다.
- 매 시도마다 증상, 원인 가설, 바꾼 점, 결과를 구분한다.
- 세 번째에도 실패하면 검사를 우회하지 말고 `BLOCKED`로 전환한다.
- 요구사항이 모호해도 기존 문서와 코드로 낮은 위험 결정을 할 수 있으면 보수적으로
  진행한다. 데이터 손실, 공개 범위, 비용, 인증처럼 결과가 크게 달라질 때만 묻는다.
- 관련 없는 기존 검사 실패는 숨기지 않는다. 작업 전에도 실패했는지 비교하고
  현재 작업과의 인과를 보고한다.

## 7. 변경 유형별 필수 검토

| 변경 유형 | 주 책임 | 필수 검토 | 최소 증거 |
|---|---|---|---|
| 저장·마이그레이션 | 데이터 신뢰성 엔지니어 | 호환성, QA | 이전·손상 fixture와 덮어쓰기 방지 |
| 장면·상태 명령 | 프런트엔드 아키텍트 | 교육 UX, QA | 순서·선택·undo 단위 검사 |
| 학생 문구·도움말 | 초등 국어 교사 | 작가·편집자, 학생 대변인 | 비채점·비자동삽입 검토 |
| UI·반응형 | 교육 UX 디자이너 | 접근성, 학생 대변인 | 키보드·터치·대표 크기 흐름 |
| Excel·시트 | 호환성 엔지니어 | 데이터 신뢰성, 교실 운영 | 최신·이전·손상 왕복 |
| 테스트·릴리스 | QA·릴리스 책임자 | 기능 주 책임 | 재현 가능한 명령과 결과 |

## 8. 작업 카드 완전성 검사

작업 카드는 아래 항목이 하나라도 없으면 실행할 수 없다.

- 작업 ID와 선행 작업
- 학생·교사 가치
- 주 책임과 필수 검토 페르소나
- 허용 파일과 금지 범위
- 사전 점검
- 번호가 있는 구현 절차
- 3~7개의 관찰 가능한 인수 조건
- 정확한 검증 명령
- 중단·되돌리기 조건
- 상태표 갱신 방법

## 9. 세션 종료 보고

아래 형식을 사용한다. 실행하지 않은 검사를 통과했다고 쓰지 않는다.

```text
결과: DONE / BLOCKED / 변경 없음
작업 ID:
학생·교사에게 달라진 점:
변경 파일:
검증 증거:
남은 위험:
상태표 변경:
다음 READY 작업: (실행하지 않음)
커밋 / 푸시 / 배포: 각각 실제 상태
```

## 10. 계획 변경 규칙

- 제품 범위나 교육 목표가 바뀌면 상세 설계와 완성 실행 계획을 먼저 갱신한다.
- 순서·의존성만 바뀌면 상태표와 해당 작업 카드를 갱신한다.
- 구현 중 새 위험을 발견하면 현재 카드의 인수 조건을 몰래 넓히지 않는다.
  현재 작업을 안전하게 끝낼 수 없으면 막힘으로 기록하고 별도 작업을 만든다.
- 완료된 카드의 기록은 지우지 않는다. 후속 수정은 새 작업 ID를 만든다.
