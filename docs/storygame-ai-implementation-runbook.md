# storygame AI 구현 런북

- 기준일: 2026-09-13
- 대상: Chat, Codex Work/로컬, 사람 검토자
- 목적: **필요한 문맥과 검증만 사용하면서 milestone을 끊기지 않고 안전하게 진행**하는 공통 절차
- 현재 상태: `docs/storygame-development-status.md`
- 작업 계약: `docs/tasks/storygame-atomic-task-cards.md`
- 실행 환경: `docs/operations/github-first-hybrid-development.md`

## 1. 핵심 원칙

1. 한 번에 하나의 작업만 `IN_PROGRESS`로 둔다.
2. **한 세션에 한 작업만 수행해야 한다는 제한은 없다.** 현재 작업이 `DONE`이고 다음 의존 작업이 명확하면 같은 세션에서 계속한다.
3. 저장소 전체를 먼저 읽지 않는다. 현재 상태 → 현재 카드 → 영향 소스/테스트 순으로 문맥을 확장한다.
4. 검증은 변경에 가장 가까운 증거부터 시작하고 필요할 때만 넓힌다.
5. 이미 같은 commit에서 CI가 통과한 검사는 Work에서 이유 없이 반복하지 않는다.
6. 제품 계약, 호환성, 사용자 데이터 보호를 바꾸는 결정만 사용자 확인을 요구한다.
7. main merge, 공개 배포, force push, 데이터 파괴, 외부 비용, 권한/비밀정보 변경은 명시적 승인 없이는 하지 않는다.

## 2. 세션 시작 — 2분 경로

### Work/로컬

1. `npm run status:check`
2. dirty files가 있으면 보존한다. 기존 사용자 작업을 지우거나 덮어쓰지 않는다.
3. 현재 작업 branch/PR이 있으면 그 기준선으로 맞춘다.

### GitHub Chat

1. 실제 `main`, 작업 branch/PR, 필요한 상태 항목만 조회한다.
2. 로컬 상태를 확인했다고 주장하지 않는다.

### 공통

1. `docs/storygame-development-status.md`에서 현재 `READY` 또는 `IN_PROGRESS`만 확인한다.
2. 해당 원자 작업 카드의 관련 항목만 읽는다.
3. 영향을 받는 소스와 가장 가까운 테스트를 읽는다.
4. 결정이 필요한 경우에만 상세 설계/ADR/목업의 해당 절을 추가로 읽는다.

**반복 금지:** 장기 로드맵, 전체 완료 이력, 모든 카드, 모든 ADR을 세션 시작마다 순회하지 않는다.

## 3. 작업 계약

별도 계획 파일을 만들지 않는다. 카드와 상태표에 정보가 이미 있으면 다시 쓰지 않는다.
필요하면 다음만 내부/대화에 짧게 정리한다.

```text
작업 ID / milestone:
한 문장 목표:
수정 가능 범위:
비목표:
인수 조건:
최소 검증:
중단 조건:
```

## 4. 상태 전이와 연속 실행

```text
BLOCKED --(의존성 충족)--> READY
READY --(실제 편집 시작)--> IN_PROGRESS
IN_PROGRESS --(인수 조건 + 최소 검증 통과)--> DONE
IN_PROGRESS --(중단 조건)--> BLOCKED
DONE --(다음 의존 작업 명확)--> 다음 READY를 IN_PROGRESS로 전환하고 계속
```

규칙:

- 동시에 둘 이상의 `IN_PROGRESS`를 만들지 않는다.
- 다음 작업이 현재 milestone의 직접 후속이며 선행 조건이 충족되면 사용자 응답을 기다리지 않고 계속한다.
- 완료 이력은 보존하되 상태표에 장문의 작업 일지를 추가하지 않는다.
- milestone이 끝나거나 중단 조건이 발생했을 때만 사용자에게 큰 체크포인트를 보고한다.

## 5. 구현 절차

### 5.1 발견

- 실제 입력 → 상태 → 저장/플레이 흐름에서 현재 변경이 닿는 경로만 확인한다.
- 이미 수정된 파일이면 먼저 diff를 읽고 의도를 보존한다.
- 새 구조를 만들기 전에 기존 컴포넌트/함수/토큰/fixture를 재사용할 수 있는지 확인한다.

### 5.2 최소 완결 구현

- 관찰 가능한 인수 조건 하나를 먼저 고정한다.
- 그 조건을 만족하는 최소 범위로 수정한다.
- 관련 없는 리팩터링과 기능 확장은 섞지 않는다.
- 새 의존성/서비스/전면 재작성은 제품 가치가 명확하지 않으면 추가하지 않는다.
- 생성 파일은 원본/생성기를 먼저 수정한다.

### 5.3 연속 진행

작업 하나가 완료되면:

1. 실제 실행한 검증만 기록한다.
2. 의미 있는 체크포인트면 commit/push한다.
3. 다음 작업의 의존성과 범위를 빠르게 확인한다.
4. 안전하면 바로 다음 작업을 시작한다.

작은 작업마다 긴 회고, 전체 문서 재탐색, 모든 검증 재실행을 하지 않는다.

## 6. 최소 검증 사다리

검증은 아래 단계 중 **현재 변경에 필요한 수준까지만** 실행한다.

### V0 — 문서/지침/메타데이터

- 링크, 경로, 문서 간 충돌, 중복만 확인
- 코드 build/test 불필요

### V1 — 국소 로직/데이터

- 가장 가까운 단위/회귀 테스트
- 타입/린트 영향이 있으면 `npm run check`
- 전체 `npm test`는 기본값이 아님

### V2 — UI/상호작용

- 관련 자동 검사
- 대표 viewport/실제 흐름 1~2개
- IME/focus/scroll 등 변경과 직접 관련된 것만 수동 확인

### V3 — 호환성 민감 변경

다음이면 관련 fixture/회귀 범위를 넓힌다.

- 저장/복구/마이그레이션
- Excel/시트 형식
- 공용 story schema/runtime
- 이전 작품 호환

### V4 — 전체 릴리스 게이트

다음일 때만 전체 `npm test`와 필요한 smoke를 기본 요구한다.

- 릴리스 후보
- 의존성/빌드 체계 변경
- 넓게 공유되는 공통 코드 변경
- 여러 핵심 사용자 흐름을 동시에 건드린 변경
- CI/로컬 결과가 달라 원인 격리가 필요한 경우

### 중복 검증 금지

- 동일 commit에서 CI가 통과한 `npm run check`/`npm test`를 Work가 다시 돌리지 않는다.
- UI 한 부분을 바꿨다고 모든 화면/viewport를 반복 검증하지 않는다.
- 현재 변경과 무관한 과거 회귀를 매 작업마다 다시 수행하지 않는다.
- 테스트를 통과시키기 위해 기존 검사를 삭제/약화하지 않는다.

## 7. 변경 유형별 최소 증거

| 변경 | 최소 증거 |
|---|---|
| 문서/지침 | 링크·경로·충돌 확인 |
| 국소 로직 | 관련 단위/회귀 + 필요 시 check |
| UI | 관련 자동 검사 + 대표 실제 흐름 |
| 저장/마이그레이션 | 이전/손상 fixture + 덮어쓰기 방지 |
| Excel/시트 | 최신/이전/손상 왕복 중 영향 범위 |
| 캐릭터 이미지 | 기준본 비교 + 필요한 geometry/alpha/ground 검사 + 실제 무대 확인 |
| 릴리스 | CI + 전체 필요한 회귀 |

캐릭터 이미지 변경은 `docs/decisions/character-pose-normalization-v1.md`를 따른다. 모든 코드 작업에서 이미지 QA를 반복하지 않는다.

## 8. 실패와 재시도

- 같은 원인의 수정은 최대 3회 시도한다.
- 재시도마다 증상/가설/변경/결과를 짧게 구분한다.
- 3회 실패하면 우회하지 말고 `BLOCKED`로 전환한다.
- 관련 없는 기존 실패는 숨기지 않되 현재 작업과 인과가 없으면 고치기 위해 범위를 확장하지 않는다.
- 요구가 조금 모호해도 기존 계약으로 저위험 결정을 할 수 있으면 진행한다.

## 9. 중단 조건

다음일 때만 기본 진행을 멈춘다.

- 데이터 손실 또는 이전 형식 파괴 가능성
- 인증, 공개 범위, 외부 비용, 개인정보/권한 결정 필요
- 사용자 결정끼리 충돌하고 기존 계약으로 해석 불가
- 다른 작업자의 변경과 충돌하여 보존 전략이 불명확
- 3회 재시도 실패
- 다음 단계가 실제 BLOCKED
- main merge/배포/force push가 필요

그 외에는 **묻기보다 안전한 다음 작업을 계속 진행하는 것이 기본**이다.

## 10. 완료 보고

큰 checkpoint 또는 milestone 종료 시에만 다음 형식으로 압축 보고한다.

```text
완료: 무엇이 바뀌었는가
검증: 실제 실행한 것과 결과
GitHub: branch / commit / PR
다음: 자동으로 이어갈 수 있는 다음 작업 또는 필요한 사용자 결정
미검증: 있으면 이유만
```

실행하지 않은 검증을 실행했다고 쓰지 않는다.
