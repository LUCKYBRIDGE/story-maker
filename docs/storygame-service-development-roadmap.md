## 0. 한눈에 보는 결론

> 현재 다음 작업은 [완성 실행 계획 §11](storygame-completion-execution-plan.md#11-u1-화면-정합화-실행-계획)의
> U1이다. 아래 초기 진단의 파일 줄 수·5개 검사·한 단계 백업은 2026-08-23 기록이며
> 최신 구현 상태가 아니다. 현재 구현 사실은 아키텍처 개요, 완료 증거와 READY는
> 개발 상태표를 따른다. 옛 백로그의 이미 DONE인 작업을 다시 시작하지 않는다.


현재 제품은 단순한 화면 시안이 아니다. 학생이 로그인 없이 이야기 구상, 챕터 구성, 대사·해설 작성, 이미지 연출, 플레이, Excel 저장·불러오기까지 수행할 수 있는 **기능형 MVP**다. 특히 편집본과 플레이 버전을 분리한 점, 화자와 이미지를 별개로 다룬 점, 창작 메모를 플레이에서 숨긴 점, 3·4·5단계 이야기 구조와 이어쓰기 템플릿을 제공한 점은 교육용 창작 도구로서 방향이 좋다.

그러나 지금 상태를 곧바로 “완전한 서비스”라고 부르기는 어렵다. 가장 큰 이유는 기능 수가 부족해서가 아니라 다음 네 기반이 아직 약하기 때문이다.

1. **작품 보존 신뢰성**: 현재 작품의 주 저장소는 브라우저 `localStorage`이고, 백업은 한 단계뿐이다. 브라우저 데이터 삭제, 다른 기기, 저장 공간 부족, 손상된 데이터에 취약하다.
2. **사용 흐름 신뢰성**: 장면 추가 후 커서, 스크롤 유지, 모바일 키보드, 오류 위치 이동, 실행 취소처럼 실제 수업에서 반복되는 동작이 충분히 검증되지 않았다.
3. **구조적 확장성**: `StoryStudio.tsx` 5,533줄과 `globals.css` 7,306줄에 상태·도메인 규칙·화면·모달·반응형 스타일이 집중되어 있다. 작은 수정도 다른 화면에 영향을 줄 가능성이 커진 상태다.
4. **검증 깊이**: 빌드와 현재 5개 회귀 검사는 통과하지만, 테스트의 상당 부분이 소스 문자열과 정적 구조를 확인한다. 학생이 실제로 입력하고 저장하고 복구하는 상호작용은 자동 검증되지 않는다.

따라서 권장 순서는 아래와 같다.

```text
작품 손실 방지와 데이터 버전화
  → 실제 글쓰기 흐름의 마찰 제거
  → 화면·상태·도메인 로직 분리
  → 가져오기·오류·복구 UX 강화
  → 접근성·성능·오프라인 안정화
  → 그 뒤에 이미지 업로드·분기 등 확장 기능 검토
```

핵심 판단은 하나다. 이 서비스는 당분간 **“로그인 없는 기기 중심 창작 도구”**로 완성하는 것이 맞다. 자체 계정, 서버 저장, 공동 편집, 작품 커뮤니티는 기존 제품 결정을 바꾸는 별도 사업 단계다. 먼저 로컬 중심 제품을 수업에서 믿고 쓸 수 있는 수준으로 완성해야 한다.

## 1. 이번 분석의 목표와 성공 기준

### 1.1 목표

이 문서의 목표는 앞으로 무엇을 만들지 나열하는 것이 아니라, 다음 개발자가 아래 질문에 바로 답할 수 있게 하는 것이다.

- 현재 어떤 기능이 실제로 구현되어 있는가?
- 학생 창작 활동에서 어디가 막히기 쉬운가?
- 어떤 기술 부채가 기능 확장을 어렵게 만드는가?
- 무엇을 먼저 해결해야 작품 손실과 회귀를 막을 수 있는가?
- UI를 어떤 정보 구조와 상호작용 원칙으로 완성해야 하는가?
- “완료”를 어떤 증거로 판단할 것인가?

### 1.2 완전한 서비스의 정의

현재 제품 방향 안에서 “완전한 서비스”는 기능이 많은 서비스가 아니라 다음 조건을 만족하는 서비스다.

| 영역 | 완료 상태 |
|---|---|
| 첫 성공 | 처음 온 학생이 설명을 길게 읽지 않고 5분 안에 첫 장면을 만들고 플레이한다. |
| 작품 보존 | 새로고침, 실수, 불러오기 실패, 일시적 저장 오류 뒤에도 작품을 복구할 수 있다. |
| 글쓰기 | 구상에서 대본, 대본에서 장면 연출로 이동해도 입력·선택·스크롤이 예측 가능하게 유지된다. |
| 이해 가능성 | “편집 중인 내용”과 “현재 플레이에 나온 내용”의 차이를 학생이 문구와 상태 표시만으로 이해한다. |
| 교육적 가치 | 도구가 이야기를 대신 써 주지 않고, 인물의 바람·갈등·사건의 인과·결말의 변화를 생각하도록 돕는다. |
| 접근성 | 키보드, 터치, 화면 읽기, 확대 상태에서도 핵심 제작과 플레이가 가능하다. |
| 호환성 | 공식 Excel, 이전 Excel, 공개 Google 시트가 명확한 검사 결과와 함께 안정적으로 열린다. |
| 운영성 | 오류를 재현하고 원인을 찾을 수 있으며, 배포 전 자동 검사가 주요 학생 흐름을 보호한다. |

### 1.3 유지해야 할 제품 경계

다음 결정은 현재 제품의 강점이므로 당장 확장하지 않는다.

- 핵심 제작에 회원가입을 요구하지 않는다.
- 웹 편집은 주 작업 공간이고 Excel은 공식 외부 보관·교환 수단이다.
- Google 시트는 공개 자료를 한 번 읽는 수단이며 자동 저장·실시간 동기화를 하지 않는다.
- 편집본과 플레이 버전은 분리한다.
- 학생용 AI 자동 글쓰기와 이미지 생성은 넣지 않는다.
- 교사 학급 관리, 공개 작품 커뮤니티, 실시간 공동 편집은 별도 제품 결정 전에는 개발하지 않는다.

## 2. 현재 구현 상태: 사실에 근거한 기준선

### 2.1 사용자가 현재 할 수 있는 일

| 흐름 | 현재 상태 | 평가 |
|---|---|---|
| 시작 | 빈 작품, 기기 저장본, Excel, 공개 Google 시트, 세 가지 이어쓰기 템플릿, 예시 플레이로 진입 | 선택지가 충분하며 로그인 없는 진입 원칙이 분명하다. |
| 이야기 구상 | 소재, 주제, 핵심 인물, 목표, 갈등, 위험, 변화, 3·4·5단계 줄거리 작성 | 국어교육 관점의 핵심 질문이 잘 들어가 있다. |
| 챕터 흐름 | 챕터별 줄거리, 역할, 분위기, 핵심 사건, 다음 챕터 아이디어 작성 | 사건의 인과를 생각하게 하는 구조가 좋다. |
| 창작 메모 | 자유 메모, 인물·관계·장소·사건 도움 틀, 추천·직접 항목, 순서 이동·삭제 | 단일 메모칸보다 훨씬 유연하고 편집 친화적이다. |
| 대본 전체 | 한 챕터의 대사·해설을 이어 읽고 수정, 장면 추가·이동·복제·삭제 | 실제 쓰기 중심 화면이라는 제품 원칙에 맞다. |
| 장면 꾸미기 | 현재 장면 글 직접 수정, 화자 위치·이름, 캐릭터·배경, 다른 장면 배치 복사 | 텍스트와 시각 연출을 구분하면서 연결한다. |
| 이미지 선택 | 추천/전체, 검색, 태그, 즐겨찾기, 최근 사용, 현재 이미지 표시 | 108개 자료를 다루기 위한 검색 구조가 마련되어 있다. |
| 메모 참조 | 편집 중 전체·챕터·장면 메모 검색, 범위 필터, 해당 입력으로 이동 | 쓰기와 구상의 왕복을 지원하는 중요한 기능이다. |
| 저장·복구 | 자동 기기 저장, 직전 편집본, 플레이 버전, Excel 저장·불러오기 | 기본 안전망은 있으나 장기 신뢰성은 부족하다. |
| 외부 자료 | 공식/이전 Excel과 공개 Google 시트 읽기, 이미지 ID·이름 연결 검사 | 호환 계층이 이미 있고 확장 기반이 있다. |
| 플레이 | 처음 또는 선택 챕터부터 마지막 적용본 재생 | 편집 실수로 즉시 발표본이 바뀌지 않는 구조가 좋다. |

### 2.3 2026-08-23 직접 확인한 결과

## 3. 현재 설계에서 잘한 점

### 3.1 교육적으로 잘한 점

1. **인물의 목표와 갈등을 분리했다.** 단순히 “무슨 일이 일어나는가”만 묻지 않고 주인공의 바람, 방해, 실패의 결과, 마지막 변화를 연결한다.
2. **학년과 숙련도에 따라 구조를 줄일 수 있다.** 5단계가 어려운 학생은 3단계로 시작할 수 있다.
3. **이어쓰기가 백지 공포를 줄인다.** 준비된 앞이야기와 명확한 시작점을 제공하면서 이후 문장은 학생이 쓰게 한다.
4. **창작 메모와 작품 문장을 구분한다.** 구상 과정은 자유롭게 남기되 발표 화면에는 실제 대사·해설만 나온다.
5. **대사와 해설의 문법을 다르게 지도한다.** 대사는 화자와 괄호 행동을 포함할 수 있고, 해설은 상황을 서술하게 한다.
6. **도구가 작품을 자동 생성하지 않는다.** 학생의 생각과 표현을 중심에 둔다는 교육 철학이 일관된다.

### 3.2 UX에서 잘한 점

- 시작 화면에서 새 작업과 이어하기를 구분한다.
- 이야기 구성 → 장면 쓰기 → 플레이의 큰 흐름이 보인다.
- 대본 전체와 장면 꾸미기를 분리해 읽기와 연출의 목적을 섞지 않는다.
- 이미지 선택 창에 현재 선택 이미지를 고정해 “무엇을 바꾸는 중인지” 알 수 있다.
- 즐겨찾기와 최근 사용으로 이미지 탐색 비용을 낮췄다.
- 위험한 삭제는 확인하고, 불러오기와 플레이 반영 전에 백업한다.
- 모바일에서 보조 도구를 접고 글 입력을 우선하려는 설계가 반영되어 있다.

### 3.3 기술적으로 잘한 점

- 편집본과 플레이 버전을 별도 데이터로 보관한다.
- ExcelJS를 동적 불러오기 해 첫 화면에서 즉시 큰 라이브러리를 실행하지 않는다.
- Excel과 Google 시트를 같은 중간 스냅숏으로 읽어 변환 로직을 재사용한다.
- 이전 탭 이름과 일부 이전 열 이름을 계속 읽는다.
- 이미지 ID뿐 아니라 정규화한 표시 이름도 찾는다.
- 창작 메모에 정렬 순서, 생성·수정 시각, 필드 출처를 포함해 확장 여지가 있다.
- 취소 가능한 Google 시트 요청과 15MB Excel 제한이 있다.

## 4. 핵심 격차와 우선순위

### 4.1 위험도 기준

- **P0**: 작품 손실, 핵심 흐름 중단, 구조적 회귀와 직접 연결. 다음 기능보다 먼저 해결.
- **P1**: 수업 완성도, 접근성, 편집 효율을 크게 높임. P0 다음 개발.
- **P2**: 제품 범위를 넓히는 확장. 실제 사용 데이터와 별도 결정 후 개발.

### 4.2 격차 요약

| 우선순위 | 격차 | 현재 위험 | 권장 해결 |
|---|---|---|---|
| P0 | 한 단계 로컬 백업 | 삭제·손상·가져오기 실수 뒤 되돌릴 범위가 좁음 | 버전 이력, 데이터 버전, 손상 격리, 복구 화면 |

## 5. 국어교육 관점의 완성 방향

### 5.1 학습 흐름을 기능 흐름과 일치시킨다

권장 학습 순환은 다음과 같다.

```text
구상하기
  → 장면으로 표현하기
  → 앞뒤 사건 연결하기
  → 소리 내어 읽거나 플레이하기
  → 고쳐 쓰기
  → 발표용 버전에 반영하기
```

현재 앱은 구상하기·표현하기·플레이하기는 강하다. 앞으로 가장 보강해야 할 단계는 **연결 점검과 고쳐쓰기**다. 새 기능은 이야기를 대신 생성하는 기능보다 학생이 자기 작품을 다시 읽도록 만드는 기능이어야 한다.

### 5.2 비채점형 고쳐쓰기 점검

플레이 적용 직전 또는 대본 전체 하단에 다음 질문을 선택적으로 제공한다.

- 첫 장면에서 인물과 상황을 알 수 있나요?
- 주인공이 바라는 것이 행동이나 대사에 드러나나요?
- 앞 장면 때문에 다음 장면이 생기나요?
- 같은 내용을 해설과 대사에서 반복하지 않았나요?
- 갈등이 가장 커지는 장면이 있나요?
- 결말에서 인물, 관계 또는 상황이 달라졌나요?
- 소리 내어 읽었을 때 너무 긴 대사는 없나요?

이 점검은 점수나 정답 판정으로 만들지 않는다. 학생이 `확인함`, `나중에 볼래요`를 선택하는 자기 점검으로 둔다. 교사가 학생 작품을 평가하는 루브릭과 학생 화면의 창작 도움은 분리한다.

### 5.3 도움말은 단계적으로 줄어들어야 한다

모든 학생에게 모든 질문을 계속 보여 주면 화면이 활동지가 된다. 권장 방식은 세 단계다.

1. **처음 쓰기**: 짧은 예시와 구체 질문을 보여 준다.
2. **이어 쓰기**: 질문 제목만 남기고 설명을 접는다.
3. **자유 쓰기**: 빈 메모와 필요한 틀만 선택하게 한다.

학생이 도움 수준을 선택하거나, 같은 기기에서 이미 한 작품을 완성했다면 설명 밀도를 낮출 수 있다. 이 값은 작품 데이터가 아니라 기기 환경설정으로 저장한다.

### 5.4 학년 차이를 구조 선택으로 해결한다

- 저학년·처음 사용자: 처음–중간–끝, 한 챕터 한 장면부터 시작
- 중간 수준: 발단–전개–위기–결말, 인물의 목표와 방해 연결
- 고학년·숙련 사용자: 발단–전개–위기–절정–결말, 관계 변화와 복선·반복 표현 점검

현재의 3·4·5단계 선택은 이 방향에 적합하다. 다만 선택 순간에 `쉬움/어려움`이라고 낙인찍지 말고 `짧게 구성`, `기본 구성`, `자세히 구성`처럼 목적 중심으로 표현하는 편이 좋다.

### 5.5 작가·편집자 관점의 콘텐츠 원칙

- 질문은 한 번에 한 사고만 요구한다.
- “재미있게 써 보세요”보다 “누가 무엇을 원하고, 무엇이 막나요?”처럼 판단 가능한 질문을 쓴다.
- 예시는 학생 답을 고정하지 않도록 서로 다른 두 유형을 번갈아 제공한다.
- 템플릿의 앞이야기는 완결된 모범답안이 아니라 이어 쓸 여백을 남긴다.
- 대사는 실제 말투와 행동이 드러나게 하고, 해설은 시간·장소·변화를 전달하게 한다.
- 교훈을 먼저 정답처럼 제시하지 않고 사건과 선택의 결과에서 주제가 드러나게 한다.
- 모든 도움말은 플레이 결과물에 자동 삽입되지 않는다.

## 6. 현재 정보 구조와 화면 방향

2026-09-04 논의를 반영한 현재 제품 계약은 [상세 설계](storygame-detailed-design.md)
§5~8과 [화면 흐름 ADR](decisions/studio-screen-flow-v1.md)이다. 화면별 요구를
여기에서 다시 복제해 다른 구현 지침을 만들지 않는다.

| 독립 화면 | 핵심 역할 | 같은 화면 안에 둘 것 |
|---|---|---|
| 메인 | 새 이야기 만들기 / 이어만들기 | 빈/템플릿 선택, 로컬/Excel/공개 시트 선택 |
| 이야기 구성 | 작품 기본·큰 생각·장의 흐름 | 선택 장 상세, 여러 단계, 장의 후보·기본 무대 |
| 대본·컷 쓰기 | 같은 장·컷의 글과 무대 편집 | 이 장 대본 / 컷 꾸미기 두 보기, 이미지 선택, 창작 메모 |
| 플레이 | 읽고 현재 컷 고치기 | 장 시작 선택, 이전/다음, 진입 전 위치 복귀 |

메인 A의 문구와 두 진입은 사용자 결정이다. “이어만들기”가 클라우드까지 고려한
이름이라고 해서 현재 계정·클라우드 기능을 추가하지 않는다. 구성 페이지 독립은
확정, 01 목록+상세 시안은 2026-09-04 사용자 위임으로 채택했다. 원작 플레이에서는 연출만 참고한다.

장의 흐름·장 상세·파일·복구·이미지 선택을 각각 별도 필수 페이지로 늘리지 않는다.
현재 기능을 접힌 상세로 보존하고, 구상 완료율로 대본 쓰기를 막지 않는다.
단계와 장은 다대다 관계이며 개수나 작성 순서를 강제하지 않는다.

## 7. 반응형·접근성 완성 기준

치수·색·글자 기준은 [디자인 토큰](design/tokens.md), 화면별 검증 조건은

## 8. 기술 구조 개선안

### 8.1 목표 구조

새 상태 관리 라이브러리를 먼저 추가하지 않는다. React의 reducer와 순수 함수만으로도 현재 복잡도를 크게 낮출 수 있다.

```text
app/story-studio/
  StoryStudio.tsx              # 화면 조립과 최상위 흐름
  state/
    studio-reducer.ts          # 편집 명령과 UI 상태 전이
    selectors.ts               # 선택 챕터·장면·검색 결과
    history.ts                 # undo/redo
  domain/
    project-schema.ts          # 현재 스키마와 검증
    project-migrations.ts      # v1 → v2 ...
    project-commands.ts        # 장면 추가·이동·삭제·복제
    project-validation.ts      # 플레이 반영 검사
  storage/
    project-repository.ts      # 저장소 인터페이스
    indexeddb-repository.ts    # 기기 프로젝트·버전 이력
    preference-storage.ts      # 즐겨찾기·보기 설정
  import-export/
    workbook-adapter.ts
    google-sheet-adapter.ts
    import-validation.ts
  components/
    EntryScreen.tsx
    PlanningWorkspace.tsx
    ChapterOutline.tsx
    ScriptEditor.tsx
    SceneEditor.tsx
    CreativeMemoDialog.tsx
    AssetPickerDialog.tsx
    FileRecoveryPanel.tsx
    StoryPlayer.tsx
```

분리는 한 번에 재작성하지 않는다. 가장 안전한 순서는 `기준 fixture → 문서 버전·저장소 → 순수 도메인 함수 → 모달 → 각 작업 화면 → 최상위 조립`이다. 각 단계에서 기존 UI를 유지하고 테스트를 추가한다.

### 8.2 상태 모델

현재 상태는 작품 데이터와 일시적 UI 상태가 한 컴포넌트에 함께 있다. 다음처럼 구분한다.

- **작품 상태**: 제목, 구상, 메모, 챕터, 장면, 플레이 버전
- **작업 상태**: 선택 챕터·장면, 편집 모드, 열린 패널, 검색어
- **기기 환경설정**: 즐겨찾기, 최근 이미지, 도움말 밀도, 마지막 보기
- **작업 이력**: 실행 취소·다시 실행을 위한 명령 또는 스냅숏
- **가져오기 상태**: 파일 정보, 검사 결과, 미리보기, 적용 여부

작품 수정은 `setDraft`를 화면 곳곳에서 직접 호출하기보다 `ADD_SCENE`, `MOVE_SCENE`, `UPDATE_MEMO_FIELD` 같은 명령으로 모은다. 이 방식은 undo, 로그, 테스트를 동시에 가능하게 한다.

### 8.3 데이터 스키마와 마이그레이션

순수 `StoryProject` 바깥의 저장 문서에 최소한 아래 메타데이터를 추가한다.

```ts
type StoryDocumentEnvelope = {
  documentType: "story-maker-project";
  schemaVersion: number;
  project: StoryProject;
  savedAt: string;
  appVersion: string;
  assetCatalogVersion?: string;
};
```

권장 규칙:

- 새 ID는 `crypto.randomUUID()`를 사용한다.
- `updatedAt`은 표시 문자열이 아니라 ISO 시각으로 저장하고, 화면에서만 한국어 형식으로 바꾼다.
- 저장본을 열 때 무조건 현재 스키마로 마이그레이션한 뒤 검증한다.
- 알 수 없는 필드는 버리지 않고 가능한 한 보존한다.
- 손상된 저장본은 덮어쓰지 말고 별도 복구 항목으로 격리한다.
- `creativeMemos`도 배열 여부만 확인하지 말고 `normalizeCreativeMemos`를 항상 거친다.
- 챕터·장면 ID 중복, 잘못된 순서, 끊어진 연결을 정규화하거나 오류로 보고한다.

### 8.4 저장 전략: 두 경로를 구분한다

#### 경로 A — 현재 제품 원칙을 유지하는 로컬 완성형, 권장

- StoryRepository: 저장 기술과 UI를 분리하고 현재 `localStorage`를 먼저 adapter로 감싼다.
- IndexedDB: 긴 작품 크기, 저장 할당량과 10~20개 복구본 요구를 측정한 뒤 전환하는 우선 후보
- localStorage: 즐겨찾기, 마지막 보기, 작은 환경설정만 저장
- Excel: 사용자가 보관하는 공식 외부 버전
- Google 시트: 읽기 전용 가져오기

이 경로에서도 기기 저장은 서버 백업이 아니다. 화면에 “이 기기에 저장됨”이라고 정확히 말하고 중요한 작품의 Excel 보관을 안내한다.

#### 경로 B — 여러 기기에서 이어 쓰는 클라우드 서비스, 별도 제품 결정

- 인증과 작품 소유권 설계
- D1: 프로젝트·챕터·장면·메모·버전 메타데이터
- R2: 업로드 이미지와 내보낸 파일
- 충돌 정책, 개인정보 처리, 삭제·보존 정책

현재 `.openai/hosting.json`에는 D1과 R2가 없고, 제품 문서도 자체 서버 저장을 제외한다. 따라서 경로 B를 지금 코드에 반쯤 넣지 않는다. 이 원칙과 맞지 않던 Drizzle·D1 예제와 미사용 인증 실험 코드는 2026-09-03 저장소 정리에서 제거했다.

### 8.5 자동 저장

- 입력마다 전체 JSON을 즉시 쓰지 않고 300~800ms 지연 저장한다.
- 저장 중 새 입력이 오면 마지막 상태만 쓴다.
- `visibilitychange`, `pagehide`에서 남은 저장을 마무리한다.
- 저장 성공 시 마지막 저장 시각을 갱신한다.
- 할당량 부족, 직렬화 실패와 저장소 오류를 서로 다른 메시지로 안내한다.
- 큰 수정, 가져오기, 플레이 반영 전에는 자동 체크포인트를 만든다.
- 같은 내용의 연속 체크포인트는 중복 저장하지 않는다.

### 8.6 실행 취소·버전 이력

두 층으로 만든다.

1. **짧은 실행 취소**: 현재 세션의 장면 추가·이동·복제·삭제, 메모 삭제, 대량 값 변경
2. **자동 버전**: 5분 간격 또는 중요한 작업 직전의 프로젝트 스냅숏

텍스트 입력은 브라우저 기본 undo를 존중하고, 앱 전체 undo가 글자 단위 편집을 가로채지 않게 한다. 삭제 직후에는 토스트의 `되돌리기`가 가장 쉬운 1차 복구다.

### 8.7 Excel·Google 시트 변환

현재 하나의 중간 스냅숏을 사용하는 방향은 유지한다. 다만 다음을 보강한다.

- 본문·메모 값은 앞뒤 공백과 줄바꿈을 원문 그대로 보존한다.
- ID, 열 이름, 종류, 위치처럼 구조 판정에 필요한 값만 `trim`한다.
- 가져오기 결과를 `오류`, `경고`, `안내`로 나눈다.
- 각 문제에 탭 이름, 행 번호, 열 이름, 현재 값, 해결 방법을 포함한다.
- 치명적 오류가 없으면 미리보기에서 챕터·장면·메모 수와 바뀌는 내용을 보여 준다.
- 적용 전 현재 편집본의 체크포인트를 만든다.
- 공식 양식 버전을 시작 탭 또는 숨은 메타 탭에 기록한다.
- 파일명은 `작품제목_20260823_1432.xlsx`를 기본으로 한다.
- Google 요청에는 명시적 시간 제한과 탭별 상태를 둔다.
- 공개 시트가 아닌 경우 “공개 설정” 또는 “Excel로 내려받기” 두 해결 경로를 제시한다.

ExcelJS 클라이언트 청크가 약 940KB이므로 동적 로딩은 유지한다. 불러오기·내보내기 중 UI 멈춤이 실제로 측정되면 Web Worker로 옮긴다. 라이브러리 교체는 호환성과 서식 검증 비용이 커서 측정 없이 먼저 하지 않는다.

### 8.8 이미지 자료

- 목록용 160~320px 썸네일과 플레이용 원본을 분리한다.
- 자산 카탈로그에 원본 크기, 파일 크기, 종횡비, 안전 영역, 얼굴 방향을 기록한다.
- 첫 화면에는 이미지를 선로딩하지 않는다.
- 현재 챕터의 기본 배경·인물만 우선 로딩한다.
- 선택창은 `loading=lazy`, 화면 밖 렌더 최소화, 이미지 오류 대체 문구를 사용한다.
- 같은 작품·인물·구도 묶음의 배치 설정을 작품 기본값으로 저장하고 챕터 예외를 허용하는 기존 계획을 별도 도메인 모델로 구현한다.

학생 이미지 업로드를 도입한다면 파일 형식·용량·저작권·개인정보·배경 제거 실패까지 함께 설계해야 한다. 단순 파일 input만 추가하는 것은 완성 기능이 아니다.

### 8.9 CSS와 디자인 시스템

2026-08-24 `docs/design/tokens.md`를 실제 종이색·민트·금색·코랄 UI에 맞춰 정리했다. 이후 디자인 변경도 이 문서와 실제 CSS 변수를 함께 갱신한다.

개선 순서:

1. 실제 CSS 변수에서 색·글자·간격·모서리·그림자를 추출해 공식 토큰으로 정리
2. 접근성 대비를 검사해 상태색 보정
3. 8~11px 글자와 44px 미만 조작 목록 작성
4. 시작·구상·대본·장면·플레이·모달 단위로 스타일 파일 분리
5. 반복되는 미디어 쿼리를 모바일/태블릿/데스크톱 기준으로 통합
6. 새 컴포넌트는 토큰 이외의 임의 색상과 간격을 추가하지 않도록 규칙화

CSS 전면 재작성은 금지한다. 화면별로 분리하고 시각 회귀 확인을 거치며 이동한다.

### 8.10 보안·개인정보

- 학생 이름, 학교, 연락처를 요구하지 않는 현재 원칙을 유지한다.
- 시트 주소와 파일 내용은 서버 로그로 보내지 않는다.
- 외부 URL은 Google Sheets ID 형식만 허용하는 현재 방식을 유지한다.
- 업로드 기능 전에는 MIME, 실제 파일 시그니처, 용량, 이미지 디코딩 실패를 검사한다.
- 스프레드시트로 내보낼 때 수식으로 해석될 수 있는 입력의 처리 방침을 테스트한다.
- 오류 분석 도구를 도입하더라도 작품 본문과 메모를 기본 수집하지 않는다.
- 서버 저장을 도입하면 미성년자 데이터 보존·삭제·보호자/학교 정책을 먼저 결정한다.

## 9. 테스트와 품질 보증 전략

### 9.1 현재 테스트의 의미

현재 5개 검사는 다음을 잘 보호한다.

- 시작 화면 서버 렌더링
- 공식 Excel 양식 구조
- 이전 저장본과 창작 메모 기본 호환
- 예시·이어쓰기 템플릿의 챕터/장면 데이터
- 주요 기능 문구·자료 파일 존재·일부 코드 규칙

반면 소스 문자열이 존재하는지를 확인하는 검사가 많아, 버튼을 눌렀을 때 상태가 실제로 바뀌는지까지 보장하지 않는다.

### 9.2 권장 테스트 피라미드

#### A. 순수 도메인 테스트 — 가장 먼저

- 장면 추가·삽입·이동·복제·삭제 후 순서
- 챕터 삭제 후 소속 장면과 메모 연결 처리
- 중복 ID와 잘못된 참조 검출
- 3·4·5단계 구조 변환
- 플레이 반영 유효성 검사
- 창작 메모 정규화와 필드 이동
- 스키마 v1→v2 마이그레이션

#### B. 가져오기·내보내기 테스트

- 공식 최신 Excel 왕복
- 이전 양식 왕복
- 긴 글, 따옴표, 쉼표, 줄바꿈, 앞뒤 공백, 한글 조합
- 빈 메모와 직접 항목
- 없는 이미지, 잘못된 챕터 ID, 중복 순서
- 공개 Google 시트 탭 일부 누락과 요청 취소
- 파일명 버전 시각

#### C. 컴포넌트 상호작용 테스트

- 새 장면을 만들면 본문에 초점
- 장면 삭제 후 되돌리기
- 모달 열기·Tab 순환·Escape·초점 복귀
- 메모 검색 결과에서 실제 입력으로 이동
- 플레이 반영 전/후 상태 표시
- 저장 실패 메시지

#### D. 브라우저 핵심 흐름 테스트

최소 시나리오:

1. 빈 작품 → 제목 → 챕터 → 대사 → 플레이 반영 → 플레이
2. 이어쓰기 템플릿 → 빈 장면 작성 → 앞뒤 플레이
3. 메모 만들기 → 추천 항목 추가 → 검색 → 해당 메모 수정
4. Excel 저장 → 다시 불러오기 → 동일 내용 확인
5. 외부 파일 오류 → 현재 작품 유지 → 오류 위치 확인
6. 새로고침 → 기기 저장본 복구
7. 모바일 크기에서 입력 → 키보드 → 장면 추가 → 플레이

대표 화면 크기는 390×844, 768×1024, 1024×768, 1440×900을 유지한다.

### 9.3 배포 전 문턱

모든 배포 후보는 다음을 통과해야 한다.

- lint와 TypeScript
- 도메인·가져오기 단위 테스트
- 프로덕션 빌드
- 핵심 브라우저 흐름
- 접근성 자동 검사와 수동 키보드 검사
- 번들 크기와 주요 이미지 전송량 비교
- 최종 변경 범위와 개인정보·비밀정보 확인

## 10. 초기 단계별 실행 로드맵(역사·장기 참고)

G0~G6의 실제 완료 여부는 상태표가 우선한다. 다음 UI 작업 순서는 U1 카드만 따른다.

일정은 팀 규모에 따라 달라지므로 날짜 대신 선행 조건과 완료 증거로 관리한다.

### 단계 0 — 기준선 고정

목표: 현재 기능을 잃지 않고 구조 개선을 시작할 수 있게 한다.

작업:

- 현재 큰 변경을 검토 가능한 단위로 정리
- 핵심 사용자 흐름 9개를 문서와 테스트 시나리오로 고정
- 데이터 스키마 v1 샘플, 최신/이전 Excel 샘플, 손상 샘플을 테스트 자료로 보관
- 실제 디자인 토큰과 화면 크기 기준 확정
- 성능 기준선 기록

완료 증거:

- 현재 5개 검사와 새 핵심 smoke가 반복 통과
- 기준 샘플로 import/export 결과가 재현됨
- 어떤 파일이 기준 문서인지 팀이 합의함

### 단계 1 — 작품 손실 방지

목표: 학생이 실수하거나 브라우저가 중단돼도 작품을 되찾을 수 있게 한다.

작업:

- `schemaVersion`, ISO 시각, UUID 도입
- 저장소 인터페이스 분리
- 지연 자동 저장과 명시적 저장 상태
- 자동 체크포인트와 최근 버전 복구
- 삭제 직후 되돌리기
- Excel 파일명에 저장 시각
- 손상본 격리와 복구 화면

완료 증거:

- 새로고침·탭 종료·저장 실패·가져오기 실패 시나리오 통과
- 최근 버전에서 작품 복원 가능
- 이전 v1 저장본과 Excel이 계속 열림

### 단계 2 — 글쓰기 흐름 완성

목표: 학생이 화면 조작보다 글의 흐름에 집중한다.

작업:

- 새 장면 초점, 장면 전환 스크롤 유지
- 대본/장면 왕복 위치 유지
- 모바일 키보드 대응
- 장면 검색과 이동
- 비채점형 고쳐쓰기 점검
- 오류 요약에서 장면으로 바로 이동
- 창작 메모의 챕터·장면 연결 UI

완료 증거:

- 대표 기기 크기에서 빈 작품부터 첫 플레이까지 막힘 없음
- 20개 이상 장면의 챕터에서도 현재 위치를 잃지 않음
- 오류를 보고 한 번의 선택으로 문제 입력에 도달

### 단계 3 — 구조 분리와 회귀 방지

목표: 이후 기능을 안전하게 추가할 수 있는 코드 구조를 만든다.

작업:

- 도메인 명령과 selector 추출
- reducer/history 도입
- 저장·import/export 계층 추출
- 모달과 주요 작업 화면 분리
- CSS 토큰 정합화와 화면별 분리
- 문자열 존재 테스트를 동작 테스트로 점진 전환

완료 증거:

- 핵심 도메인 로직이 React 없이 테스트 가능
- StoryStudio가 화면 조립 역할 중심으로 축소
- 기능별 수정이 관련 테스트와 스타일 파일 안에서 리뷰 가능

### 단계 4 — 수업 환경 안정화

목표: 네트워크·기기·접근성 차이가 있는 교실에서 안정적으로 사용한다.

작업:

- 앱 셸과 핵심 이미지 오프라인 캐시
- 이미지 썸네일과 로딩 최적화
- 키보드·화면 읽기·확대·저동작 접근성
- Google 시트 시간 제한과 상세 오류
- 긴 작품과 저사양 기기 성능 점검
- 작품 본문을 수집하지 않는 최소 오류 관측 체계 검토

완료 증거:

- 한 번 연 뒤 네트워크가 끊겨도 로컬 편집·플레이·Excel 작업 가능
- 대표 저사양 태블릿에서 장면 입력 지연이 수업을 방해하지 않음
- 키보드만으로 핵심 흐름 완료

### 단계 5 — 선택적 확장 결정

아래 기능은 사용성 자료와 명시적 제품 결정 후 각각 독립 프로젝트로 진행한다.

- 학생 이미지 직접 추가
- 여러 단계 장면 분기와 선택지
- 교사용 출력물·수업 진행 자료
- 여러 기기 저장과 공동 편집
- 작품 공유 링크 또는 공개 갤러리

한 번에 둘 이상을 시작하지 않는다. 특히 업로드·계정·공개 공유는 개인정보와 운영 책임을 크게 바꾼다.

## 12. 측정 지표

학생 콘텐츠를 서버로 수집하지 않아도 관찰 수업과 로컬 테스트로 다음을 측정할 수 있다.

### 핵심 성공 지표

- 첫 진입부터 첫 플레이까지 걸린 시간
- 교사 도움 없이 첫 장면을 완성한 학생 비율
- 저장·불러오기·복구 성공률
- 플레이 적용 오류 후 스스로 문제 장면을 찾은 비율
- 대본과 장면 꾸미기 왕복 후 위치를 잃은 횟수
- 한 차시 안에 고쳐쓰기를 1회 이상 수행한 비율

### 품질 지표

- 저장 실패·손상 복구 실패 건수
- import 실패의 원인별 분포
- 첫 화면 JS와 이미지 전송량
- 긴 작품에서 입력 후 화면 반응 시간
- 자동 테스트가 보호하는 핵심 흐름 수
- 키보드만으로 완료 가능한 흐름 수

### 교육 관찰 지표

- 주인공의 목표와 방해가 작품에 드러나는가
- 장면 사이 인과가 있는가
- 대사와 해설의 역할을 구분하는가
- 결말에서 인물·관계·상황의 변화가 드러나는가
- 학생이 도움 틀을 답안 복사보다 사고 도구로 사용하는가

이 지표는 학생을 점수화하기 위한 것이 아니라 UI와 수업 설계를 개선하기 위한 관찰 기준이다.

## 16. 최종 제안

이 제품의 차별점은 “게임처럼 보이는 이야기 편집기” 자체가 아니다. **학생이 생각을 구상하고, 실제 문장으로 쓰고, 장면으로 확인한 뒤, 다시 고쳐 쓰게 만드는 순환**이 차별점이다. 앞으로의 개발은 이 순환을 더 빠르고 안전하고 이해하기 쉽게 만드는 데 집중해야 한다.

가장 좋은 다음 모습은 화려한 기능이 많은 서비스가 아니라 다음과 같은 서비스다.

- 학생은 작품이 사라질까 걱정하지 않는다.
- 어디를 쓰는 중인지 잃지 않는다.
- 도움을 원할 때만 도움 틀을 펼친다.
- 플레이를 보고 스스로 한 번 더 고친다.
- 교사는 파일과 기기 문제를 해결하느라 수업을 멈추지 않는다.
- 개발자는 한 기능을 고쳐도 다른 화면이 깨질까 두려워하지 않는다.

이 기준을 만족한 뒤에야 이미지 업로드, 선택지, 클라우드 저장 같은 확장이 제품을 풍부하게 만든다. 그 전에 확장하면 현재의 좋은 교육 설계가 복잡한 기능 속에 묻힐 가능성이 크다.
